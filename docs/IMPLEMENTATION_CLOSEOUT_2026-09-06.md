## 3. 구현된 흐름

**Initialize**: 설치본 Git 루트 확인 → 필요한 상태/측량 디렉터리 준비 → 없는 바통 생성 →
Git 실효 속성 확인 → private 추적 규칙 → 없는 머신 설정 생성 → 바로가기.
앱 데이터 동기화와 원격 생성은 하지 않으며 Start의 선행 내부 단계도 아닙니다.

**Start**: 설정·작업트리 확인 → fetch → 바통/미게시 작업 확인 → 정상 종료·핸들 정착 →
앱별 알려진 구조 검증과 백업·적용 → 전 앱 성공 → 로컬 기준과 바통 처리 → 앱 실행 → 보고.
바통 push 성공 응답 뒤 의무적인 재조회는 없습니다. 앱 적용 전에 바통을 선점하지 않습니다.

**Finish**: fetch·바통 확인 → 기존 변경을 커밋 없이 스냅숏 → 전 앱 종료·핸들 정착 →
순차 Prepare(검사·백업·앱 정합화·결과 트리) → 전 앱 Ready → 공동 후보 commit/push →
게시 확인 → 로컬 기준 저장 → Complete(백업·임시 폐기) → 게시된 작업트리 반영 → 보고.
Complete는 Prepare와 같은 스크립트 버전으로 실행하기 위해 checkout 변경보다 앞에 있습니다.

미커밋 변경과 기존 미푸시 커밋을 보존합니다. Git 객체 생성은 사전 브랜치 커밋과 다릅니다.
공통부는 앱 payload를 해석하거나 staging 경로를 소유하지 않습니다.
전달 계약은 RunId, RemoteCommit, BaselineCommit과 PREPARED_TREE / LOCAL_BASE_TREE입니다.
앱 결과에는 [Codex]/[Claude] 접두사를 붙여 루트 RESULT와 구분합니다.

마지막 세션 출력 뒤 생기는 공백까지 모두 압축 때문이라고 단정할 수 없습니다.

다음 항목은 **미구현 제안**입니다. 새로운 계약이나 자동 기능 승인이 아닙니다.

1. 단계별 처리 바이트·레코드·Git 호출·DB 조회 수와 비용을 분리해 가장 큰 중복부터 확인합니다.
2. 같은 실행에서 기준/원격이 공유하는 불변 Git blob/tree 검증 결과를 재사용하는 방안을 검토합니다.
3. 적용 전후 바뀌지 않은 원문·투영의 재읽기를 줄일 수 있는지 확인합니다. mtime·길이만으로 동일성을 인정하지 않습니다.
   앱 외부 변경을 놓치지 않는 근거와 캐시 무효화가 먼저이며 불명확하면 전체 검사 또는 중단으로 돌아갑니다.
4. 세션별 Git 프로세스와 DB 조회를 batch/일관된 읽기 단위로 묶는 방안을 검토합니다.
5. 전역 참조는 이미 로컬 스냅숏당 한 번 색인합니다. gzip 마커도 이미 구현돼 있으므로 새 기능으로 다시 제안하지 않습니다.
6. 변경 없는 F-S-F, 원문 한 페이지 증가, 새 대화, 삭제, Archive, 원격 변경, 같은 길이 손상,
   실패·Cancel을 비교해 판정/바이트/복구 보장이 그대로인지 확인한 뒤 속도를 비교합니다.

검사 자체를 없애기, 버전 번호만으로 캐시 승인, 성공한 앱 플래그로 다음 실행 생략,
구조를 공통부로 끌어올리기, 상시 감시 프로세스 추가는 이 개선 범위가 아닙니다.

## 7. 남은 불일치와 재개 위치

**Reactivate — 사용 보류.** 사용자 요구는 Vault Archived → Active 게시 후 종료이며
실제 앱 반영은 별도 Start입니다. 현재 두 Reactivate의 `Publish-Reactivation` 뒤에는
`Stop-...Gracefully`, `Invoke-...Start`, `Set-...Baseline`, 앱 재실행이 남아 있습니다.
이 때문에 두 앱 Reactivate는 요구 충족 완료로 판정하지 않습니다.
이번 마감에서는 불일치를 명시하고 코드를 추가 변경하지 않았습니다.
재개 시 이 호출 범위를 먼저 바로잡고, 앱 데이터·프로세스·비교 기준을 건드리지 않는지 격리 검증합니다.

그 밖에 다른 물리 PC의 실제 UI 연속 사용, 미측량 앱 구조와 불투명 필드 의미는 계속 미확인입니다.
성공 로그가 미측량 구조의 안전한 쓰기를 허가하지 않습니다.
