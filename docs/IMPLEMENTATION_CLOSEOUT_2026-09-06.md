## 3. 구현된 흐름

**Initialize**: 설치본 Git 루트 확인 → 필요한 상태/측량 디렉터리 준비 → 없는 바통 생성 →
Git 실효 속성 확인 → private 추적 규칙 → 없는 머신 설정 생성 → 바로가기.
앱 데이터 동기화와 원격 생성은 하지 않으며 Start의 선행 내부 단계도 아닙니다.

**Start**: 설정·작업트리 확인 → fetch → 바통/미게시 작업 확인 → 정상 종료·핸들 정착 →
앱별 알려진 구조 검증과 백업·적용 → 전 앱 성공 → 로컬 기준과 바통 처리 → 앱 실행 → 보고.
바통 push 성공 응답 뒤 의무적인 재조회는 없습니다. 앱 적용 전에 바통을 선점하지 않습니다.

**Finish**: fetch·바통 확인 → 기존 변경을 커밋 없이 스냅숏 → 전 앱 종료·핸들 정착 →
순차 Prepare(검사·백업·앱 정합화·결과 트리) → 전 앱 Ready → 공동 후보 commit/push →
게시 확인 → 로컬 기준 저장 → Complete(백업·임시 폐기) → 게시된 작업트리 반영 → 보고.
Complete는 Prepare와 같은 스크립트 버전으로 실행하기 위해 checkout 변경보다 앞에 있습니다.

미커밋 변경과 기존 미푸시 커밋을 보존합니다. Git 객체 생성은 사전 브랜치 커밋과 다릅니다.
공통부는 앱 payload를 해석하거나 staging 경로를 소유하지 않습니다.
전달 계약은 RunId, RemoteCommit, BaselineCommit과 PREPARED_TREE / LOCAL_BASE_TREE입니다.
앱 결과에는 [Codex]/[Claude] 접두사를 붙여 루트 RESULT와 구분합니다.

### 개정 전 비용과 변경 감지 실측

개정 전 Codex Start는 `Verify-StoredSessions`를 기준/원격에 각각 실행하고,
`Prepare-Local`을 적용 전후 각각 실행합니다. 로그에는 61개 로컬 비교가 두 번 나옵니다.
변경 없는 gzip 마커 재사용은 이미 작동하며 해당 로그에 6회 나옵니다.
전수 읽기를 모두 없애지는 못한 상태입니다. 이 검사는 자동 재측량과 다릅니다.

| Codex 로그 경과 구간 | 관측 단계 | 구간 길이 |
|---|---|---:|
| +20.2s ~ +262.8s | 저장 자료 검증, 적용 전 로컬 검사·비교·매핑 확인 | 242.6초 |
| +262.8s ~ +385.9s | 앱별 백업·적용 | 123.1초 |
| +385.9s ~ +427.8s | 적용 결과 검사 | 41.9초 |
| +427.8s ~ +560.9s | 적용된 로컬 비교 기준 재구성 | 133.1초 |

이는 단계 경계 시간이지 각 해시·SQLite·Git 함수의 단독 비용이 아닙니다.
Finish에도 같은 중복이 얼마나 있는지 별도로 확인해야 합니다.

이후 앱 목록 API에서 확인된 Codex 10개 대화의 **각 최신 rollout 하나씩**, 합계 463.44 MiB를
SHA-256으로 읽었습니다. 전체 61세션이나 모든 과거 페이지를 측정한 값이 아닙니다.

| 환경 | 1회차 | 2회차 | 3회차 |
|---|---:|---:|---:|
| Windows PowerShell 5.1.26100.9168 | 1.147초 | 0.770초 | 0.706초 |
| PowerShell 7.6.5 | 0.691초 | 0.638초 | 0.636초 |

앱을 닫지 않아 공유 읽기 스트림과 `Get-FileHash -InputStream -Algorithm SHA256`을 사용했습니다.
파일 열기·읽기·해시 계산을 측정했고 프로세스 시작, DB 경로 조회, JSON 분석 시간은 포함하지 않았습니다.
OS 캐시는 비우지 않았으므로 차가운 디스크의 보장값은 아닙니다.
각 읽기 전후 크기·수정 시각은 같았고, 여섯 측정의 해시도 파일별로 동일했습니다.
따라서 이 10개 최신 원문의 해시 계산 자체가 기존 9분 실행 시간을 설명하지는 않습니다.

### 선택한 변경 감지 기준

마지막 질문 문자열만 비교하는 대신, **앱이 현재 가리키는 최신 rollout 경로와 파일 전체 SHA-256**으로
대화 변경을 먼저 가려냅니다. 예전 경로를 고정해 계속 읽으면 페이지 전환을 놓치므로,
현재 canonical 세션과 최신 파일의 연결부터 확인합니다. 경로는 이 PC의 직전 관측과 비교하며
서로 다른 PC의 절대경로가 같아야 한다는 뜻이 아닙니다.

같은 질문을 편집·재전송한 뒤 이 대화의 최신 페이지가 새 파일로 전환된 사례를 확인했습니다.
새 페이지에는 동일 canonical 세션 ID와 이전 물리 페이지의 특정 byte/ordinal 끝을 가리키는
`history_base`가 있었습니다. 기존 큰 페이지도 남아 있었습니다.
따라서 문장이 같더라도 경로·해시 변화로 이번 변경을 감지할 수 있었습니다.
편집 동작이 언제나 같은 방식으로 페이지를 생성한다는 일반 법칙까지 증명한 것은 아닙니다.

| 관측 | 개정된 처리 방향 |
|---|---|
| 최신 경로 또는 해시 변경 | 해당 대화의 변경과 참조 관계를 확인하고 필요한 분석·운송 자료 재구성 |
| 최신 경로·해시 동일, 관련 상태도 동일, 이전 검증 있음 | 기존 본문 분석 결과와 운송 자료 재사용. 같은 본문을 다시 전체 분석하지 않음 |
| 새 canonical 세션 | 신규로 검증·처리. 기준에 없다는 이유만으로 고아 판정하지 않음 |
| 새 페이지 또는 되돌리기 참조 경계 | 새 메타와 predecessor 연결 및 실제로 필요한 참조 구간 확인 |
| 원격 객체 변경 | 로컬 최신 해시가 같아도 원격 변경은 별도로 수신·3자 비교 |
| 삭제·이동·DB·인덱스·배치 변경 | 본문 진행 여부와 별도로 상태를 검사하고 영향받은 대상 처리 |
| 기준·검증 자료 없음, 실제 검사 규칙 변경 | 재사용 근거를 확보하기 위한 검사 수행. 앱 버전 번호만으로 이를 강제하지 않음 |

최신 파일이 바뀌었다고 다른 대화나 모든 과거 페이지의 바이트까지 바뀐 것은 아닙니다.
재검사는 변경 대화의 필요한 의존 관계로 제한합니다. 원격·기준이 공유하는 검증된 불변 Git 객체는 재사용합니다.
최신 파일 해시는 과거 모든 파일·DB·첨부의 무결성을 한 번에 증명하는 서명이 아닙니다.
이것은 정상 대화 진행에 대한 **본문 재분석 선별 기준**이며 기존 전송 무결성, 삭제 증거와 상태 검사는 유지합니다.

### Start와 Finish의 개정 대상

**Finish**: 가벼운 세션 목록·최신 경로 조회 → 최신 원문 해시 비교 → 변경 대화만 본문·계보 분석 →
별도의 삭제/Archive/원격 상태 판정 → 필요한 정합화 → 변경 없는 운송 자료 재사용 → 전 앱 성공 시 공동 게시.

**Start**: 원격 fetch → 검증된 동일 Git 객체 재사용 → 로컬 최신 경로·해시와 관련 상태 변화 확인 →
필요한 대상만 적용 → 실제 변경 대상과 영향받은 관계 검증 → 변경 없는 비교 자료 재사용.
적용 뒤 전체 세션 비교 자료를 무조건 다시 만드는 중복을 줄입니다.

공통부에 앱 본문 판정·캐시 구조를 넣지 않습니다. 이번 개정으로 새 캐시 파일, 설정값,
상시 감시 또는 앱별 성공 플래그를 만들기로 결정한 것도 아닙니다.
기존 비교 기준과 운송 마커를 먼저 활용하며, 추가 저장이 꼭 필요하면 그 필요성과 소유 범위를 따로 제시합니다.

Claude도 최대한 빠르게 끝내는 대상입니다. 그러나 이번 해시·페이지 전환 실측은 Codex 사례입니다.
